# M5: performance and release. Guide for contributors

M5 makes bibers fast and ships it. Read `docs/PLAN.md` (§1 targets) and `docs/M2.md` (conventions) first.

**The one rule:** performance work never changes behaviour. Every output, log line and exit code stays byte-identical. `cargo xtask corpus` must stay 776/776 and every benchmark workload must stay `ok`.

## Targets (PLAN.md §1) and baseline (2026-10-13, Apple M-series, release build)

## Tools

- **Workloads:** `tools/bench/gen_workloads.py`, written to `$BIBERS_BENCH_DIR` (default `target/bench`). biber's goldens (`expected.bbl`, `biber.txt`) are made once with `tools/bench/run.py --golden`. They take minutes, so worktrees share the coordinator's set: `export BIBERS_BENCH_DIR=/Users/ben/bibe-rs/target/bench` (read-only for you).
- **Benchmark:** `cargo build --release -p bibers && tools/bench/run.py [--runs N] [workload…]`. It reports best and median time, peak RSS and the speedup over biber, and FAILs if a `.bbl` differs from biber's.
- **Profile:**
  - `cargo build --profile profiling -p bibers` (release with debug info);
  - `samply record --save-only --unstable-presymbolicate -r 4000 -o p.json.gz -- target/profiling/bibers -q --noconf doc.bcf`;
  - `tools/bench/profile_report.py p.json.gz [--filter REGEX] [--callers REGEX]` gives self time, inclusive time, and who calls a hot function.

## Where the time goes (baseline profile of `examples-x46`)

- **Reading, 23%:**
  - `fetch::bibtex::cache_data`: 10%, almost all `perlish::nfd` on every value, with no ASCII fast path.
  - `create_entry`: 11% (names, dates, source maps).
  - The btparse parse: 6%.
- **Per-list processing, 39%:**
  - `process_entries_post`: 17% (name hashes, `ls::viv`, label data).
  - Uniqueness: 7%.
  - `generate_sortinfo`: 6%.
  - `generate_contextdata`: 4%.
- **`.bbl` rendering, 26%:**
  - `set_output_entry`: 15%.
  - `encode_output`: 3%, the Perl-encoding layer simulation running even for UTF-8.
  - `dangling_comma_cleanup`: 2%.
- **Cross-cutting:**
  - `memcmp` is 15% of self time, and malloc/memmove/SipHash a further 15–20%. They come from string-keyed `BTreeMap`s (`Entry` fields and slots, `serde_json` slots), `BlxOptions::get` (5%), `Entry::get_field` (7%), `DataModel::def`, `format!`, and cloning.
- **Startup (`examples-x1`, about 7 ms):**
  - `.bcf` parsing: 13% of the run.
  - Option registry declaration and `process_backendin`: 5%.
  - PCRE2 compilation in `FetchOpts::new`: 5%.
  - `initopts` / `DataModel::new` / `BiberOptions::with_defaults`: about 10%.

## Work packages (phase 1, in parallel)

| Package | Owns | Scope |
|---|---|---|
| model | `bibers-core/src/model/` (and `model::dump`) | Typed, compact hot state: interned field names (a `Sym` type), small sorted vectors or `Vec`-backed maps instead of `BTreeMap<String, …>`, typed replacements for the hot `slots` (`PerlData`), cheaper name-list and section maps. **Keep the public API source-compatible** (`get_field(&str)` etc. keep working) so the other packages' code keeps compiling; add faster entry points alongside. `model::dump` must keep producing biber's exact JSON (the phase tests check this). Also memory: the 200 MB target for 17k entries. |
| input | `crates/btparse`, `crates/latex-recode`, `pipeline/fetch*`, `pipeline/sourcemap.rs`, the regex cache in `perl-compat` | `nfd`/`nfc` fast paths (ASCII and quick-check), fewer copies in `cache_data`/`create_entry`, btparse lexer and parser, LaTeX decoding, source map engine, compiling regexes once per run instead of per call. |
| process | `pipeline/{entries,labelalpha,uniqueness,sort,lists,resolve}`, `output/`, `crates/ucollate` | Name hashing and `ls::viv`, uniqueness (and the `uniquelist-4000` and `crossref-2000` shapes: algorithmic fixes where biber is super-linear, PLAN §4.9), sort-key generation and collation, context data, `.bbl` rendering, and a UTF-8 fast path in `encode_output`. |
| release | `config/`, `bcf/`, `datamodel.rs`, `crates/bibers/src`, CI workflows, packaging docs | Startup: `.bcf` parsing, the option registry, `BlxOptions::get` (5% of large runs: cache or index it), datamodel construction, `--version` < 5 ms. Release engineering: a GitHub Actions release workflow that builds static binaries (macOS universal, Linux x86_64/aarch64 musl, Windows x86_64) on tag, with checksums; `README` install and drop-in instructions (latexmk `$biber`, arara, TeXstudio, Overleaf-style setups); and a `bibers` vs `biber` speed table in the README generated by `tools/bench`. |

## Phase 2 (in parallel)

| Package | Owns | Scope |
|---|---|---|
| memory | data representation: `model/` (incl. `liststate.rs`), the fetch cache (`RunState` bibcache, `rawdata`), output buffers | Peak RSS on `examples-x184` from 540 MB to < 200 MB. Known costs (heap peak 462 MB):<br>- list state's remaining JSON maps (per-entry `fields`, per-name data: typed structs and `Sym`-keyed maps);<br>- per-entry `.bbl` templates plus the 39 MB text alive together at render (free per list or stream, keeping the citekey-order template building the BB-028/shared-list quirks rely on);<br>- the 50 MB bibcache and per-entry `rawdata` copies (drop or share once no longer needed);<br>- `Value` strings (`Box<str>`/shared), `NamePart.initial` (`Option<Vec<String>>`: two allocations per initial);<br>- entry map buffers (exact-size `SymMap`s). |
| parallel | control flow: `pipeline/` phase drivers, `output/bbl.rs` render loop, `run.rs` | Multi-threading with `rayon` (or `std::thread::scope`) where work is independent:<br>- parsing (`.bib` files; entries within a file once split);<br>- per-entry field handling in `create_entry`;<br>- per-entry list phases (`process_entries_pre/post`, `generate_sortinfo`, …);<br>- sort-key generation;<br>- per-entry `.bbl` instantiation;<br>- sections and data lists where independent.<br>Logs, warnings, hash-order emulations and every quirk must come out in exactly the serial order: collect per-item results and merge in order. Add a `--threads N` CLI extension (DC-05x; default = available cores; `1` = serial) and **serial == parallel tests**: the whole corpus and every bench workload byte-identical at 1 and N threads, repeated runs identical. Targets: `examples-x46` < 250 ms, `examples-x184` < 1 s, `uniquelist-4000` < 200 ms, `crossref-2000` < 100 ms. Small single-threaded wins on the way are welcome. |

The packages overlap where per-entry data is produced and consumed, so keep to these boundaries:
- **memory** changes types and storage, and keeps their APIs source-compatible where it can.
- **parallel** changes loops and drivers, and treats the data types as given.

Merge `main` into your branch before reporting.

## Conventions

- **Measure first and last.** Report before/after numbers from `tools/bench/run.py` on all workloads in your final report, plus the top of a new profile.
- **Readable code first.**
  - Prefer better data structures and avoiding work over micro-tricks.
  - `unsafe` only with a measured win and a `// SAFETY:` comment.
  - Keep the `Biber.pm:<line>` citations and biber's iteration orders; a faster structure must iterate in the same order wherever order is observable.
- **Hash maps:** a faster hasher (e.g. `rustc-hash`/`ahash`) is fine for maps whose iteration order is never observable. Check each one.
- **Stay in your package.** The model package changes model internals; the other packages may use new model entry points once they land on `main`. Keep edits outside your package small and additive.
- **Before reporting:**
  - `cargo fmt --all`;
  - `cargo clippy --workspace --all-targets -- -D warnings`;
  - `cargo test --workspace`;
  - `cargo xtask corpus` (776/776);
  - `tools/bench/run.py` (all `ok`).
